## F0 · 从首页进入一局

1. 新增一个小型目录表，每项记录稳定 ID、中文名、一句话目标、支持人数、视口大小和已接入的启动函数。沿用 `campaign`、`infinite` 标识。新增 `run_gun`、`deep_dive`、`sub_courier`、`tide_race`、`boss_duel`。目录由已实现的条目组成。开发半成品可通过测试直接构造。
2. 统一首页保留原入口并增加「玩法大厅」。原单机菜单也能进入同一目录。玩法卡可用方向键、回车、鼠标或轻触选择，返回恢复刚才焦点。创建、加入、受邀重连均走现有房间。读屏内看得见的名称、人数、按钮，在触控时有对应的命中范围。
3. 单人路径为「模式 → 选择幕／海域／赛道 → 简短操作提示 → 开始 → 暂停或结算 → 重试／换目标／返回玩法大厅」。双人专属卡直接提供建房和加入。暂停菜单可继续或退出到原入口。退出仍在进行的局使用现有确认交互。
4. 主循环明确持有当前单人模式会话。处理该会话的事件、固定更新和绘制后结束本帧分派。退出清理触控、键盘边沿、相机、音效循环、旧 HUD 和固定步长余量。重进原战役时用原本的战役时钟、画布和快捷键。
5. 每个模式实现可脱离窗口运行的初始状态和一次固定步更新。建议接口为 `start(options, seed, slots)`、`step(held_by_slot, actions)`、`snapshot()`。同一模式的单人、房间共用这份规则。绘图读取状态，音效消费一次性事件，菜单负责结构化结果。直接用普通 Python 模块或小类，随第一个模式提取真正共用的代码。
6. 内容数据放在 `assets/modes/<mode_id>/`，用有版本的 JSON 记录场地、路线、数值和稳定标识。正式美术放在 `assets/images/modes/<mode_id>/`。地图碰撞和触发器以逻辑坐标保存。素材清晰度、图片裁边或屏幕像素比改变时，关卡几何仍由内容数据决定。

### 时间、坐标和控制

- 每步 `1/60` 秒，位置单位为逻辑像素，设计表秒数在读入时换为整数 tick。规则统一处理同一 tick 的输入、位移、接触、目标和结算。模式文档指定边界同时触发时的优先级。生成内容使用本局 seed。结算、音画和重连可从稳定 ID 找回对象。
- 横版突围、快递、竞速的逻辑视口为 960×540，寻宝和 Boss 对决为 800×540。地图可大于视口。主界面现有房间画布横屏 960×720、竖屏 480×720 是外层布局。内部世界等比映射至可用矩形，触控先减偏移再除缩放。竖持设备可把操作区放在画面下方，同样能完成开局。联机继续执行双方与房主方向一致的规则。
- 画面大小改变时只重算投影、HUD、按键区，世界坐标、平台、当前命中区和回合时间保持连续。保留宽高比，保证两个方向看到相同的有效场地。横版合作采用共享镜头，竞速由各自镜头跟自己的飞鱼。
- 按住输入与按下瞬间分别采集。玩家在两个模拟 tick 之间快速点一下，边沿也要送达一次。模式内显示当前岗位的动作名和按键。手机同一根手指只拥有一个控件，移动与主动动作可同时使用。触摸取消、方向暂停、窗口失焦均清空按住项。恢复后重新触碰才动作。保留 PC 的 F11。
- 单人暂停、系统失焦和浏览器后台冻结模拟，恢复首帧重置累加时间。联机以房间暂停原因为准。音效事件由 `match_id / epoch / event_id` 去重，重连从该快照起接续，避免把旧音效和结算动画再播一遍。

## F1 · 将新模式送入现有双人房间

### 大厅、兼容与运行分派

- 保持现有 v1 预览及 v2 战役、无限客户端可用。拟在统一服务的 `/health` 增加 `extra_modes`，值为「已启用联机模式 ID → 内容／协议兼容修订号」的小表。新客户端按实际连接目标读取这一项，只在对端声明支持时，在原 v2 `hello` 附带双方交集。缺该字段按旧大厅连接。主网页的自动重连也要在连接前拿到目标能力。服务离线不阻塞三个单人入口。
- 新服务允许省略 `hello.extra_modes`，将该席位视为只支持战役与无限。大厅回传服务及在场客户端的可用交集。建房预选新模式可以先保存在房主客户端，两席支持后提交。不兼容的队友得到更新提示，仍能一起选原玩法。运行中持有效席位重连须匹配该模式修订号，失败时给出「请更新后重连」，保留正常的重连期限。
- 新模式的 `room_settings` 只接受对应的 `mode_options`。`run_gun` 用 `stage` 与 `run_type`（`story` 连续、`practice` 练习），`sub_courier` 用 `order`，`tide_race` 用 `track`，`boss_duel` 用 `boss`。具体 ID 见模式表。新模式只接受配置中存在的值。`deep_dive` 首版只出现在单人可玩列表。房主有效修改会递增 `settings_revision`，两席重新准备。相同设置重复提交结果相同。
- `MatchRoom.start` 按模式选工厂。现有两种玩法继续创建 `OnlineGame`。新增房间适配只提供房间真正用到的生命周期、输入、推进和快照。重点改 `Room.clear_input/run/handle` 的输入清零与超时、`Host.remove` 的 `all_players[…].alive` 假设、`LAN.frame/battle` 的战役字段访问。通过模式策略分派离席和结果，避免给潜艇或飞鱼伪造一套战役角色。
- 服务器持有碰撞、工具、货物、成绩、技能和胜负。客户端显示快照，并可在两次快照间做纯视觉插值。横跳落地、计时冲线、换岗、Boss 命中均由服务器确认。房间按仍需操作的席位判断断线、后台、旋转和暂停，进入暂停时冻结所有有效游戏计时。竞速已冲线者成为观赛席位，其断开或离开时另一位选手继续比赛。沿用当前宿主重连期限，基线默认 120 秒。
- 新玩法联网结束后双方可在结果页查看同一赛果。「再来一局」两席确认后换 `match_id`。选择「回房间」由宿主结束已结算会话、清空准备、增加设置修订号并广播大厅，允许再次选玩法。主动离席先交给该模式按时间与身份裁决，再清理连接。横版保留独自继续的选择，竞速保留有效过线时间，快递与 Boss 产生各自规定的终态。结果页和大厅均可显式离开房间。

### 拟新增线协议

以下消息只对互相声明支持的新模式生效。沿用原有消息大小上限、连接席位、单调序号、`match_id`、准备版本与暂停规则。旧输入仍服务旧玩法。

```json
{"type":"mode_input","match_id":"<当前对局>","epoch":2,"seq":41,"x":0.8,"y":-0.2,"held":1}
```

```json
{"type":"mode_action","match_id":"<当前对局>","epoch":2,"seq":42,"action":"jump"}
```

```json
{"type":"mode_action","match_id":"<当前对局>","epoch":2,"seq":43,"action":"cast_1","target":[720,410]}
```

| 字段或事件 | 开发约定 |
| --- | --- |
| `x/y` | 有限实数，范围 −1 到 1，右、下为正。含义由当前模式和岗位解释。方向改变及时发送，按住时定期发当前状态，建议 20 Hz，低于现有约 0.4 秒输入静默清零阈值。 |
| `held` | 位 1、2、4、8 分别表示主、副、交互、辅助动作按住。每种岗位有自己的有效掩码。瞬时动作以 `mode_action` 为准，按住位不会再次触发同一个跳跃或换岗。 |
| `aim8` | 仅横版突围的 `mode_input` 可选此字段。0–7 从向右开始按画布顺时针排列，用于移动和瞄准独立的触控。无显式瞄向时按该模式的方向和最后朝向取值。 |
| `action/target` | 动作使用各文档的白名单。需要瞄点的 Boss 释放动作额外带两个 0–1000 的整数，按完整竞技场宽高还原。服务器将其投影到可施放范围。其余动作省略目标。 |
| `epoch` | 由服务器生成的输入代次。换幕、全队检查点重置、换岗、换边及整局暂停后恢复时递增，同时清空先前按住状态和待处理动作。上一代迟到的输入不能影响当前岗位或回合。 |
| 排序 | 两种新消息与旧的暂停等对局动作共用一个席位发送序号。按连接到达顺序接收。一帧内多个合法边沿按权威接收顺序入列，下一模拟步只消费一次。双方同 tick 冲线或同时倒下按对应玩法的规则判定。 |
| 权限 | 当前模式、角色、有效阶段和冷却决定动作是否生效。房主与普通玩家在比赛中使用同一套判定。客户端发出的成绩、货物、位置、对方席位均不属于输入字段。 |

`Room.snapshot` 的外层继续承载 `mode / match_id / tick / phase / paused / pause_reason / players / world_size`。新世界使用 `world.kind="mode"` 和 `world.schema=1` 标识，包含 `content_id / content_version / epoch / phase / view_size / actors / runtime / result`。外层 `phase` 保持房间生命周期，内层 `phase` 可表示航行、交接或换边。地图和贴图用内容 ID 本地取。快照传动态对象 ID、当前姿态、必要计数和结算值。客户端先检查 `kind` 再选择绘制器，含新世界的结算帧也能完整显示。

### 结果确认和再开

同一局的终态带稳定 `result_id` 和仍需确认的席位。客户端绘制终态后用 `mode_action: result_seen` 确认可重建结果。确认只代表已显示，完整两席的结果页继续等待玩家选择。`rematch_ready` 为该席位选择再来一局，两席都选择才启动新局。`back_lobby` 为回房间意向，有一人选择就取消再赛投票，两席均已看到赛果后回到大厅。临时掉线的席位可在原期限内回来看到终态。只剩一席且已确认离席结算时，可直接返回首页。

横版中队友正式离席时，剩余席位可发 `continue_solo` 或 `end_run`。Boss 换边说明页可发 `round_ready`。这些动作只在所属阶段和席位有效。结果确认可在终态暂停时处理，所有选择在服务器按同一对局、代次和席位去重。任一席都能在结果页显式离开，两个席位均已退出或过期后回收房间。

### 本地记录

- 原生用标准库 SQLite，在 `Path.home() / ".ttgames" / "modes-v1.sqlite3"` 保存。主 Web 用 IndexedDB 的 `ttgames-main-modes`，Phaser 用 `ttgames-phaser-modes`。每个库带 schema 版本。局内热循环只使用内存。
- 寻宝签收以 `run_id + treasure_instance_id` 去重，一笔事务更新回执和图鉴。最高成绩按海域更新。竞速按 `track_id + track_version + rules_version` 存最佳 tick 和与它对应的航迹，比较和替换放在同一事务，防止跨标签页后完成的慢成绩覆盖快成绩。
- 签收或安全抵港后才写，竞速正常完赛后才写。读不到旧版本时按可识别的字段读取。写入失败保留本局结果，并显示「本次记录仅在当前会话有效」。重复进入结果页、网络重复快照和点击重试不再发奖。多人比赛只展示本场结果，寻宝记录和竞速个人最佳按各自文档归属。
- PC 的游戏目录、Web 的离线缓存、联机重连的 `sessionStorage` 与玩家记录各有生命周期。应用升级只替换游戏资源。轨迹版本不兼容时仍可在旧成绩行显示所属版本，当前赛道只加载匹配航迹。

## 先验证哪一条链

F0 用首个真实玩法走「首页 → 模拟五秒 → 暂停十秒 → 恢复 → 结算 → 原战役」。对比有效 tick、触控释放和返回后的输入。F1 用同一模式让原生客户端与主网页各占一席，覆盖准备版本、旋转暂停、断线恢复和再次开局。随后验证一位旧 v2 客户端与一位新客户端能共同进入原战役。各模式新增测试优先覆盖下文的专属边界，完整跨端清单见[整体验收](06-integration.md)。
