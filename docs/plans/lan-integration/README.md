# TTgames 单机与局域网联机融合 · 最终实施方案

本文件是开发与验收入口。基线为 `f6e5b84`。实施前记录实际 HEAD、工作区、依赖与基线测试结果。按本文三个阶段开发，保留已有用户改动。分阶段验证，整合入口以全部验收通过为发布条件。

## 一、确认的产品规格

| 编号 | 要求 |
|---|---|
| 01 | PC 原生版和 Web 首页均提供「单机模式」「创建房间」「加入房间」。 |
| 02 | **同一设备、方向和窗口尺寸下，单机与联机共用战斗、商店、暂停、结算的绘制、布局和操作入口。** 原控件位置与命中区域一致。联机权限决定控件是否可操作。 |
| 03 | 创建、加入和准备可以使用独立房间页。开打后，队友、共享资源、重连和离场信息使用共用界面的既有状态区域。 |
| 04 | 电脑使用键鼠，手机使用触控。Web 单机保留现有离线玩法。 |
| 05 | 两台原生 PC 对局时，由创建者电脑开服，创建者占 P1、加入者占 P2。 |
| 06 | 原生 PC 加手机时，电脑运行服务，两端均可创建并占 P1。 |
| 07 | 两部手机对局时，电脑停在首页提供服务，两部手机分别占 P1、P2，电脑无玩家席位。 |
| 08 | PC 到首页即提供服务。点击创建才分配房间。每个服务同时承载一个双人房间。 |
| 09 | 四位数字房间码保留前导零。邀请链接含宿主局域网地址和房间码。创建时为创建者预留 P1。 |
| 10 | 单机与联机都支持战役选关和无限模式。战役从选定关卡顺序推进。联机战役首版使用简单、中等、困难三个预设。 |
| 11 | P1 设置玩法、方向，以及战役的难度和起始关。双方准备且方向一致后开打。修改配置后双方重新准备。 |
| 12 | 同局统一横屏或竖屏。战斗中有在场玩家方向不符时暂停，恢复一致后继续同局。 |
| 13 | 服务器权威处理伤害、金币、生命和购买。临时断线保留席位，重连回原对局。 |
| 14 | 联机无限模式各自决定继续或退出。一人阵亡时队友仍可战斗，选择继续只复活自己。 |
| 15 | 无限模式任一方主动退出时，另一位保留对局、章节与比分，只收到一次非阻塞提示「队友已退出，你可以继续游戏」。 |
| 16 | 提供服务的电脑玩家退出至首页后，服务继续运行。无限模式两人离场后回收房间。关闭宿主游戏程序会停止其服务。 |
| 17 | 真机验收两台原生 PC、原生 PC 加手机、两部手机。混合组交换创建者，手机组验证电脑停首页。另补桌面浏览器对桌面浏览器回归。 |
| 18 | 对照同设备单机和联机的四类界面截图及控件操作。实测战役选关、无限模式独立继续与退出、重连和 Web 离线单机。 |

已确认的控件例外。战斗 HUD 的「+ / −」在联机保留原位置和外形、禁用切关，鼠标悬停、键盘尝试或触屏点击时从原状态区域提示「仅开局可选关」。单机仍按原规则操作。联机战役在大厅选择起始关，无限模式从第一章开始。

## 二、阶段 1 · 入口、宿主、构建和房间

### 代码入口与运行职责

- 原生入口为 `run_pc.py` → `pc/main.py` → `game_core/main.py`。共享首页按三种模式分流。PC 启动后进入首页时异步启动一个独立的 aiohttp 宿主子进程，健康检查成功后显示可分享的局域网入口。开服失败时显示原因并保留单机入口。PC 加入别人的房间时连接对方宿主。
- 宿主复用 `online/server/__main__.py` 与 `online/server/app.py`，负责统一 Web 静态资源、房间 API 和同源 `/ws`。宿主独立于 Pygame 窗口，隔离进程级画布、方向、时钟和声音。监听选择当前可用的私网接口。可用地址不止一个时列出地址并明确当前用于分享的地址，排除绑定通配地址和回环地址。使用实际监听端口，兼顾多网卡与占用场景。PC 从回环创建房间时，分享 URL 仍来自宿主公布的局域网端点。
- PC 仅管理自己启动的子进程。固定端口为 8765。端口占用时保留原进程，并在首页提示该端口已被占用。宿主自动启动路径不调用旧 `web/run_web.py` 的 `release_port()`。支持无终端启动，处理缺依赖、权限错误、启动超时、静态资源缺失和关闭。原生程序退出时关闭其宿主；对局退出回首页不停止宿主。验证由任意工作目录启动，以及开服失败后单机可用。
- 原生使用项目现有 aiohttp 依赖实现客户端，标准 PC 安装纳入该依赖；浏览器沿用 `online/web/bridge.js`，原生和浏览器共用 `online/shared/protocol.py` 的消息契约。原生网络 I/O 与游戏帧循环分离，输入、快照和重连只跟随当前会话。保留私网 Host 与浏览器同源 Origin 检查，原生端按目标地址构造匹配的 Origin。TLS 校验沿用客户端信任链。

### 统一 Web 构建和命令

1. 保留 `python run_web.py` 与 `python run_web.py --build-only` 的入口习惯。构建步骤复用 `web/run_web.py`，正式发布的统一入口使用 `game_core/main.py` 启动同一游戏，按模式连接联机桥。整合现有 `online/tools/build_web.py` 的联机展示及协议打包部分，浏览器包只包含客户端所需模块。两个运行入口使用同一份可发布 Web 产物。Web 正常服务由同一个 aiohttp 宿主提供页面、`/rooms` 和 `/ws`。
2. `python run_pc.py` 及打包后的 PC 应用使用预构建资源。用户启动后无需构建、下载运行时或运行第二条命令。保留 `run_web.py` 已有的 HTTP/TLS 参数和证书引导可达性。局域网 HTTP 在线游玩使用同源 WS，可信 HTTPS 使用同源 WSS。跨宿主通过邀请链接进行页面级导航。HTTP 手机访问显示适用的离线状态，离线保存和断网冷启动按可信 HTTPS 验收。
3. 将桥接脚本、样式、入口 HTML、Python 归档、WASM 与运行时资源纳入同一次构建的内容版本和离线资源清单。健康检查、建房 API 和联机状态请求走网络。缓存的首页在断网时仍能进入单机，联网操作显示明确反馈。验证已有缓存升级，覆盖旧前端连接新服务器时得到可理解的版本错误，刷新后加载匹配的版本。
4. 本地源码启动与打包版本共用实际宿主逻辑。使用干净环境运行两个入口，验证桥接资源存在、服务头与现有隔离设置一致、运行时无外部资源请求，以及端口占用时原进程仍存活。现有独立联机入口可作为阶段内诊断对照。

### 房间与消息契约

| 入口 | 约束与结果 |
|---|---|
| `GET /health` | 返回服务、协议版本、构建标识和可用状态。无副作用。 |
| `POST /rooms` | 按每次用户创建生成的高熵 `request_id` 幂等处理。同一次请求重试返回同一预留，另一次请求在已有房间时返回 `409 room_in_use`。创建成功返回房间标识、四位字符串 `code`、房主凭证和邀请 URL。凭证只交给创建者，URL 只含公开定位信息。 |
| WebSocket `hello` | 校验协议版本和四位码。首次连接可带房主凭证，重连可带席位令牌，两者互斥。有效房主凭证只能入 P1，普通加入只能入 P2。服务端原子分配席位并签发重连令牌，凭证在首次握手确认入座前，只允许同一预留恢复未完成握手。活跃 P1 连接不可被覆盖。确认入座后凭证失效，使用已保存的席位令牌重连。 |
| `room_settings` | 仅 P1 可修改未开打的配置。服务端保存 `settings_revision`，实际变更后递增并清除双方准备，再广播权威设置。 |
| `ready` / `start` | 两者都携带当前 `settings_revision`。旧版本请求返回配置已更新，客户端按最新快照重新确认。`start` 仅 P1 可发起，同一大厅版本只启动一次，验证两位在场、已准备、方向一致且当前可开始。 |
| `input` / `action` | 使用已认证的席位、`match_id` 和递增 `seq`。保留现有移动归一化和输入超时清零。加入离场、个人继续、手动暂停、离场通知确认等所需控制请求，按房间阶段明确允许条件。拒绝过期会话、非当前对局及非法重放。 |

- 房间初始为空。未兑现 P1 预留默认 60 秒，失联席位默认保留 120 秒。均由服务端配置，使用单调时钟，测试可注入时钟。创建响应丢失时，重试恢复原预留；建好但首个 `welcome` 未送达时，原创建者能恢复 P1 握手。两类重试均验证并发与凭证隔离。尝试创建、加入和猜测房间码需限频，限制请求大小和消息形状。
- 分开管理房间 ID、席位 ID 与对局 ID。席位 ID 一直是 1 或 2，不按数组位置重排。重连令牌绑定宿主地址、房间实例及席位。新对局更新 `match_id` 并清理旧输入与快照，保留仍属于该房间的有效席位身份。换房或主动离场才清除对应重连凭证。协议变更同步更新服务端、原生和 Web 版本，以及缓存版本。
- 大厅 P1 可关闭房间，P2 可离开并释放席位。战斗中临时断线在超时前保留席位并全局暂停。重连须恢复同一席位与 `match_id`，重新核对方向和准备就绪状态。断线保留期到期后，战役结束并通知在场玩家；无限模式按该席位离场处理，另一人可继续。两人均无法恢复时回收房间。
- 战役任一方主动退出结束该局并通知对方。无限模式开打后，「退出本局」始终只退出自己的席位，包括 P1；此时禁用关闭整间房的玩家操作。清理该席位输入、商店和暂停占用，撤销重连身份并阻止中途补位。其离场不会停止宿主，剩余席位仍归原玩家。退出请求带幂等标识。服务端先记录离场结果再回复并关闭连接；响应丢失时允许同一请求重取已完成回执，回执查询不能重新入座。客户端未收到结果时保留重试状态，服务端未处理的掉线仍走临时断线规则。
- 阶段 1 验收房间、身份、配置协议和三种真实设备组合的大厅链路。可用协议夹具验证离场保留原席位。阶段 3 验收离场后真实战斗继续。

## 三、阶段 2 · 共用界面、坐标和控件

### 绘制与输入契约

- `game_core/main.py` 维持统一窗口或浏览器画布与事件循环。单机从本地 `Game` 取状态，联机从 `online/adapters/presentation.py` 及服务器快照取状态。切换模式时销毁上一个对局的输入与连接上下文，清除持键、触摸、自动射击、暂停和商店状态。恢复本机视口与场景时钟。
- **拆开权威战斗坐标与本机界面坐标。** 横屏权威世界 `960×720`，竖屏 `480×720`，由房间设置决定。服务器碰撞与实体状态只使用权威尺寸。联机客户端在本机窗口投影战斗场景，保持比例和鼠标/触控坐标转换。背景铺满本机游戏窗口，不因投影出现黑边。玩家移动边界和怪物生成区域由服务器统一计算，对两位玩家采用同一权威坐标。HUD、商店、暂停、结算与触控命中区域以同一设备当前单机布局为基准，从同一套本机 UI 几何计算和绘制。世界绘制与 UI 绘制之间恢复各自的 `config.SCR`、尺寸、偏移和时钟，避免 `configure_world()` 覆盖界面布局。PC 根据房间要求调整实际窗口，手机旋转并上报实际方向；世界尺寸开打后固定。
- 复用 `game_core/game.py` 的 HUD、商店、暂停、无限继续和结算绘制与 `game_core/menu_ui.py`。当前联机跳过 HUD 并把触控交给 DOM。改为在房间阶段由大厅接管输入，战斗阶段启用共享游戏布局与触控，不叠加另一套战斗按钮。联机展示层只绘制与派发意图，禁止隐式执行本地扣金币、伤害、切关或复活。
- 快照显式提供所选玩家的 HP、角色、武器、拥有列表、冷却、装备限制与失败反馈，以及共享金币、生命、进度、阶段、结算字段。HUD 与商店依据本地真实席位读数据，P1 离场后剩余 P2 仍显示自己的状态。区分全局战斗阶段和本地弹窗，商店、继续、倒计时、暂停和重连可从真实快照恢复。

| 原有控件 | 联机行为 |
|---|---|
| 移动、射击、自动射击、技能及装备快捷键 | 沿用原键位设置与触控组件。自动射击产生常规射击输入。技能、切装备和特殊动作由服务器校验；切后台、弹窗切换、退出和方向改变时释放持键与触点。 |
| 战斗 HUD「+ / −」 | 原位、原尺寸，禁止触发切关或切章，使用可触发说明的禁用语义。鼠标、键盘和触屏命中时只提示「仅开局可选关」，不发送切关请求。 |
| 血条点击 | 将原狂暴意图交给服务器，沿用适用模式、难度及现有规则。客户端仅显示服务器结果。 |
| 商店、技能预览、购买与装备 | 预览与本地导航沿用现有行为，购买、强化和装备由服务器校验并返回状态。联机武器强化消耗共享金币，等级按武器全队共享。商店保持当前双人关闭规则，一人已离场时只等待仍在场玩家。 |
| 暂停、继续、退出确认 | 使用原布局和操作入口。手动暂停由发起席位占用，恢复只释放相应暂停原因。断线、方向不符、商店等原因仍由服务器合并处理。无限模式的个人继续、个人退出见阶段 3。 |
| 音量、画质和本地显示缩放 | 沿用本机设置。画面尺寸和绘制变换只影响本机呈现，不写入权威世界。 |
| 结算与重开 | 联机结算根据服务器结果绘制。普通战役由 P1 发起按当前配置重开，双方仍须满足开局条件。无限模式个人「继续」和「结束」走席位操作。 |

### 界面验收

在同设备、同窗口尺寸与方向、相同难度和匹配的场景状态下，保存单机／联机的战斗、商店、暂停与结算截图。测量最终屏幕或 CSS 像素上的控件边界，验证绘制区域与触控命中边界一致，可接受缩放取整造成的 1 像素误差。可见差异限于实际对局、队友和现有状态区域内的联机信息或权限。包含 `1280×720` 原生宽屏和约 `390×844` 的长屏手机，并覆盖两种方向。逐个操作控件，尤其验证联机「+ / −」的位置、提示和世界章节不变。实测双指移动并开火、键鼠设置、商店两人关闭、断线叠加手动暂停，以及回首页切换模式。

## 四、阶段 3 · 战役、无限模式与集成验收

### 战役选关

- 房主配置包含 `mode`、`orientation`，战役另有 `difficulty` 和 `start_level`。战役起始关为严格整数 `1..len(LEVEL_CONFIGS)`，拒绝布尔值或越界。无限模式固定从第一章开始，使用原内部难度规则，大厅隐藏战役难度和起始关。
- `Room.start` 从锁定的配置启动，在 `OnlineGame` 中复用 `Game._start_game(difficulty, start_level)`。双人按联机新局规则初始化装备、金币、生命和出生点。之后推进沿用战役规则，过关保留本局状态，最后一关结算不得读取第十二关。重开创建新 `match_id`，保持所选模式、起始关、难度与方向。单机原有预设、自定义难度、选关、无限模式按既有入口回归。
- 核对 `Campaign Opening/Ending`、过场和胜负结果字段，开场、战斗、过渡及胜负由服务器对局状态驱动。联机保留当前战役过场范围，共用逻辑层已有对应画面。单机已有的独立开场和片尾继续回归。

### 无限模式状态与时序

复用 `Game._begin_infinite_run` 和原无限模式刷怪、Boss 循环、数值增长、背景和音乐。双人初始化明确各自的角色、武器、冷却、HP、出生位和共享钱包。审查 `OnlineGame._damage_player`、`_resolve_leak`、巨鲸吸入、`step`、`_action`、装备和快照分支，避免走战役自动／付费复活、战役终局或普通关卡索引。无限快照含章节、Boss 轮次、背景主题、比分、死亡数、用时和对应席位状态。验证第九、第十轮与第十一轮之后的循环。

| 事件或阻塞 | 权威行为 |
|---|---|
| 其中一人阵亡 | 只将该席位置为等待选择，清除其战斗输入。仍存活的队友可作战，死亡次数按实际阵亡玩家计入共享统计。 |
| 阵亡者选「继续」 | 进入个人倒计时，拒绝重复提交导致的重置或二次复活。到期只复活提交者，延续同一章节、对局和共享比分；不会清理队友正在打的世界。 |
| 两人均倒下 | 冻结战斗模拟。双方仍能独立提交自己的选择。已启动的个人倒计时在没有其他暂停原因时继续推进，任一允许复活的席位到期后恢复战斗。 |
| 存在断线、切后台、方向冲突、手动暂停、商店或服务器故障 | 战斗与个人继续倒计时均冻结。所有这些外部暂停原因解除后，按剩余时间恢复；两人均倒下本身不计为外部暂停。 |
| P1 或 P2 主动退出 | 清理该席位资源并从全局暂停判定移除。另一人的战斗或倒计时按原状态继续，保留相同的 `match_id`、比分和章节。 |
| 最后一位离场 | 结束并回收房间，宿主继续提供新房间。 |

复活倒计时使用服务端可控时钟，累计允许继续的时间。客户端只根据快照显示本人的剩余时间。对局存活人数、在线人数和离场状态分开判断。席位退出后从输入、碰撞、敌人选目标、商店和方向检查中移除；仍被技能效果引用时保留必要的视觉数据和原席位编号，直至相关效果过期，避免快照悬空引用。处理应支持只剩 P2 的完整战斗链路。

离场提醒使用稳定的 `match_id + event_id + recipient_slot` 标识。服务器将待确认提醒保留在后续快照内，跳帧或临时断线后仍可送达。客户端在实际进入相关界面时显示一次，并记录已展示标识，以便刷新或重连时补发确认而不重复展示。提醒使用现有状态区域，不抢焦点、不暂停、不遮挡操作。收到确认或接收者已离场时回收事件。
